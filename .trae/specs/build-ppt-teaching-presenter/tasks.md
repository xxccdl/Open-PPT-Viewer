- [x] SubTask 5.3: 实现阴影、发光、柔化边缘等图片与形状效果（性能不足时按档位降级为简化效果）
- [x] SubTask 5.4: 实现表格与图表（降级）的绘制
- [x] SubTask 5.5: 实现渲染输出格式与呈现方式：输出预乘 BGRA 位图，并支持编码为 WebP/PNG 供传输（编码方式依 Task 7 的通道结论定稿）
- [x] SubTask 5.6: 实现按缩放档位渲染（低档位用于缩略图，高档位用于主视图）与设备像素比适配
- [x] SubTask 5.7: 单元测试 + 视觉回归测试（对样本语料集渲染并与基准图做像素差异比对，设置允许阈值）
- 验证：`cargo test -p ppt-render` 通过（80 项单元 + 12 项 PPTX→位图端到端）；端到端测试用真实拼装的 PPTX 验证了渐变方向、椭圆填充与描边、组合内子形状的烘焙变换、主题 accent1 文字色、确定性、多分辨率内容占比一致、缓存复用、多线程渲染；实测单页 720×540 渲染 < 80ms
- 说明：
  - SubTask 5.5 的输出格式定稿为**预乘 RGBA8**（`PixelFormat::Rgba8Premultiplied`）而非 BGRA —— 这是 tiny-skia 的原生格式，省掉一次全图遍历；编码为 PNG 时由编码器还原直通 alpha
  - SubTask 5.7 的「视觉回归」以「像素级断言（渐变方向、颜色命中数、内容占比与分辨率无关）」实现，未引入外部基准图；接入真实课件语料集后再补差异比对阈值
  - 图片填充未走 tiny-skia 的 `Pattern` 着色器（它借用位图，与 `Paint<'static>` 生命周期冲突），改为「形状路径建遮罩 + 透过遮罩绘制位图」
  - 阴影以「多层递减透明度的偏移填充」近似（tiny-skia 无内置模糊滤镜），对课件常见的浅阴影足够且不分配大缓冲

## Task 38: 渲染管线的性能真相 —— 已交付

## Task 40: 动画逐元素弹出 —— 让办公软件**按步出图** —— 已交付

老师一句话点破了 Task 39 的漏洞：
**「无法逐页弹出：弹出的都是已经显示的内容」**。

根因是架构性的：`Slide.Export` 出的是一张**拍平的整页图**，上面什么都有，
包括这一步还不该露面的答案。管线里 `render_direct` 拿到 `PlayState`
压根不看它 —— 于是每一步拿到的都是同一张「全播完」的图。

三条底线里，「按钮能点、视频能播」靠双源架构解决了，
**「元素按 ppt 逐一弹出」必须让办公软件自己画每一帧**。

### 怎么让 WPS 画「第 k 步的样子」

- [x] 实测确认（PowerShell 直调 COM）：
  **`Shape.Visible = msoFalse` 会被 `Slide.Export` 尊重** ——
  同一页导出两次，1,020,534 字节 vs 1,217,773 字节；还原后字节数完全一致
- [x] `Shape.Id` 就是 OOXML 的 `p:cNvPr/@id`，与解析器里的 `shape_id` **同值**，
  所以「哪一步该藏谁」可以两端直接对上
- [x] 每一步导出时把「这一步还不该出现」的形状隐掉，存成
  `<页码>.<已播步数>.png`；`<页码>.png` 仍是全部播完的样子
- [x] 逐元素弹出现场验证（真实课件第 1 页，4 步）：
  `0.0.png` 只有背景图 → `0.1.png` 出现圆角矩形 → `0.2.png` 出现装饰图
  → `0.3.png` → `0.png` 文字最后到位

### 算账人与出图方分工

「哪一步该藏谁」需要 OOXML 解析器，而「让办公软件画」在另一条线程上。

- [x] `ppt-convert` 只接受一份**现成的清单**：`StepPlanner`
  （`Arc<dyn Fn(usize) -> Vec<Vec<u32>>>`），它不认识 OOXML
- [x] 清单由 `ppt-app` 的 `step_hide_plans` 算出，规则**复用 `Build::visible_in`**
  —— 自研渲染内核走的也是它，两边不会各说各话
- [x] 出图方（写）与显示层（读）**共用同一个 planner**
  ⇒ 步数必然一致，帧不会错位
- [x] 解析只发生在「翻到动画那一步」或「后台出到那一页」，
  **不在打开课件那条路上**（首屏预算守住了）

### 三个踩过的坑

- [x] **`MsoTriState` 读回来是 `VT_I4` 不是 `VT_BOOL`**
  - 症状：194 张分帧全部与整页图**字节完全相同**，日志里一句错都没有
  - 根因：`as_bool` 只认 `VT_BOOL` → 每个形状都被当成「不可见」→ 谁都没藏
  - 修法：`VT_BOOL` 与 `VT_I4` 都认
  - 教训：**「什么都没发生」也是一种失败信号**，不能只看有没有报错
- [x] **老缓存会让出图任务一次都不启动**（症状：一直转圈）
  - 整页图全在了 ≠ 分帧也在了；`ready < pages` 判断漏掉了后半句
  - 修法：出图任务在分帧全部成功后写下 `steps.done` 标记，
    打开时「整页图不全 **或** 没有这个标记」才排任务（已出好的各自跳过）
- [x] **「还在排完」标志的默认值必须是「已排完」**
  - 默认 `false` ⇒ 没有任务在跑时显示层永远等下去（一直转圈）
  - 只有 `begin_warm`（任务真的开跑）有资格清零

### 已知限制（写在这里，免得下次当成 bug 查）

- 强调动画（变色、放大）**没法用静态帧表示** —— 它不改变可见性，
  办公软件导出的是「未被强调」的样子。这类步仍由自研渲染内核合成，
  误差为近似（见 Task 24）。
- 一页 N 步会多出 N 张整页 PNG（本课件 194 张 ≈ 180MB）。
  分帧只在含动画的页、且只会出一次；**缓存淘汰尚未实现**。

老师三条反馈，第一条是 Task 40 漏掉的，后两条是新问题。

### 一、「全部显示所有页面元素后再一个一个往上面砸」

- 根因：**段落级动画**（`p:txEl`，「项目符号逐条弹出」，课件里最常见的形态）

  - 实测 WPS 的 `Font` 上既没有 `Visible` 也没有 `Hidden`（两个都不存在）
  - `TextRange2.Paragraphs(i).Font.Fill.Transparency = 1` 有效：

### 二、「元素和翻页反应有点慢」

量出来的数据（改之前）：

| 操作 | 后端耗时 | 载荷 |
|---|---|---|
| 全屏整页渲染 | 62~147ms | **7.9MB** |
| 缩略图（173×97） | 263~**2193ms** | 0.1MB |

两处根因：

- [x] **后端 3 秒忙等把工作线程占满**（最大的那个）
  - 缩略图一露出来十来个请求同时发，每个都在后端死等最多 3 秒；
    老师接着翻页的那次请求只能排在它们后面 —— 手感就是「反应慢」
  - 修法①：后端死等 3000ms → **250ms**（只 absorb 一次很快的出图），
    剩下的等待交给前端轮询（**轮询不占后端线程**），间隔 150ms
  - 修法②：缩略图请求**限流到 2 个并发**，它们永远不许抢老师的操作
- [x] **传了 7.9MB 原始像素**，而那张图本来就躺在磁盘上
  - 走「读 → 解码 → 缩放 → 转预乘 → 传原始像素」，每一步都是白花的
  - 修法：`DocumentSource::raster_png_path` + `render_page` 快路 ——
    **把 PNG 文件原样传给前端**，解码与缩放交给浏览器（有 GPU）
  - 代价：写进 `decodeFrame` 的一条嗅探（PNG 固定以 `89 50 4E 47` 开头，
    原始帧的头 4 字节是宽，撞不上）
  - 缩略图不走快路（`wants_native_raster`）：那等于把整页图塞进 173×97
    的格子，39 张能吃掉几百 MB 内存

**结果：日志里「渲染偏慢」（>60ms）从每页都有变成 0 条。**

### 三、「有时会黑屏（全屏播放时）」

黑屏不是一个 bug，是一类「画布被清空了却没人再画」的故障。堵住三个口子：

- [x] **`animateFor` 的 Promise 可能永远不 settle**
  - 老师手快时，上一步动画还没演完就点下一步/翻页；旧动画要画的那张位图
    可能刚被新的一次绘制 `close()` 掉，`drawImage` 抛异常后 Promise 永不
    settle → 调用方的 `finally` 永不执行 → 画布停在「已清空、未画出」
  - 修法：动画改为**可中止**（`paintSeq` 令牌，谁后开始谁负责画），
    且 `draw` 抛异常时一律 resolve
- [x] **`paintFrame` 会拿一张已关闭的位图去画** —— 它的宽高是 0，
  于是画布被清成 0×0，之后怎么翻都是黑的。现在直接跳过
- [x] **`#fade` 黑场遮罩可能留在屏幕上**（全屏切换时用的那层）
  - 中途任何一步抛异常都会让它留在屏幕上，而 `state.presenting` 已经是
    true，再按 F5 也会被「已经在放映」挡回来 —— 彻底卡在黑屏
  - 修法：`try/finally`，**无条件收掉**

> **教训（又一次）：「什么都没发生」也是一种失败信号。**
> 段落隐藏第一版静默失败的原因是：`Paragraphs(i)` 是**带参数的属性**，
> 必须用 `DISPATCH_PROPERTYGET` 调，我用 `DISPATCH_METHOD` 调，
> 被拒之后调用点 `else { continue }` 一路静默 —— 分帧生成成功、
> 日志一句错都没有、帧的内容却和整页图一模一样。
> 现在这类「一段都没藏成」会明确报警。

## Task 42: 缓存淘汰误删画面来源 + 旧版 .ppt 自动转换 —— 已交付

### 一、「有的时候会出现显示旧版自研渲染的 ppt」

- **根因在缓存淘汰，不在渲染链路。**
  `DiskCache::enforce_budget` 从 **`root`** 递归收集文件、按修改时间删最旧的，
  上限 512MB —— 而 `root` 就是 `%LOCALAPPDATA%\OpenPPTView\cache`，
  **「办公软件出的逐页 PNG」也住在同一个 root 下**（`cache/wps/…`）。
  于是它把**画面来源当成缓存副产物删掉了**，那几页只能退回自研渲染内核。
- 实测证据：某课件第 0~10 页的整页图与 0~9 的分帧一起消失、第 11 页往后完好
  —— 正是「按 mtime 由旧到新删」的形状。

## Task 44: 「升级完了，双击课件起来的还是老版本」 —— 已交付

老师升级到最新版、退出，再双击一个 `.pptx` —— 起来的却是旧版本。

### 一、根因：关联是**分档**写的，而 HKCR 里 HKCU 优先

- ProgID 跟着安装方式走：按机器装（`C:\Program Files`）写 HKLM，
  按用户装（`%LOCALAPPDATA%\Programs\OpenPPTView`）写 HKCU。
- 这台机器上先后装过这两种：早先按用户装的那份把
  `HKCU\Software\Classes\OpenPPTView.pptx\shell\open\command`
  指向了它自己；后来按机器升级写的是 HKLM。
  **HKCR 的解析顺序是 HKCU 优先**，于是那条影子一直压着新的。
- 界面上完全看不出来：`FileExts\.pptx\UserChoice` = `OpenPPTView.pptx`，
  「默认打开方式」显示的确实就是 OpenPPTView。
- 实测（修复前）：`HKCR\OpenPPTView.pptx\shell\open\command` =
  `"C:\Users\65411\AppData\Local\Programs\OpenPPTView\OpenPPTView.exe" "%1"`
  —— 那是 9/20 22:33 装下的旧副本，文件还在磁盘上。
  同一时刻 `.pdf` 已经指向 Program Files（那份是应用自己登记的），
  所以只有 `.pptx` 有问题 —— 这个不一致本身就是「两个来源在写同一个键」的证据。

### 二、修法

- [x] `associations::status` 的「已注册」以前只看 ProgID 键在不在，
  现在还要看它的命令**指着谁**（新增 `points_here`）。键在、但指着另一个副本，
  就不算「能打开」，界面也不该说「已经是默认了」。
- [x] `repair_if_dangling` → `repair_if_needed`：把「指着另一个副本」也纳入自愈。
  但**只有装在这台机器上的那一份**才有资格改（`may_repoint` 用
  `InstallLocation` 判断）—— 否则开发时直接跑 `target\release\ppt-app.exe`
  也会把老师的 `.pptx` 抢过去，又造出一次「打开的是另一个版本」。
- [x] 安装器装完顺手 `settle_legacy_user_install`：发现有按用户装过的旧副本
  （且不是这次装的地方）就收掉它 —— 先 `--quit` 请它退出、删目录、清掉它
  写在 HKCU 的卸载登记与偏好 —— 再把 HKCU 里那几条指向它的命令改指到新位置。
  这样「双击课件 → 起来的一定是这一份」不再依赖老师先手动跑一次新版。
- [x] 设置页 / 欢迎页跟着诚实：`pointsHere` 为假时如实显示
  「注册指向的是另一个副本，点『注册到本应用』改过来」。

### 三、顺手修掉的第二个问题：装完拉起来的那份是**管理员权限**

安装程序是提权的，`ShellExecuteW` 拉起的子进程继承管理员权限。实测两条后果：

- 从资源管理器往窗口里拖课件会被 UIPI 挡掉（普通权限进程不能往高权限窗口拖放）；
- **双击课件时新起的普通权限实例，没法把文件转交给那个常驻的高权限实例**
  （消息同样被 UIPI 挡掉）—— 老师看到的是「双击了，什么都没发生」。
  实测：普通权限的 `--quit` 叫不动管理员权限的那个实例，提权的可以。

修法：`launch_app` 改成**请资源管理器代启动**（它自己是普通权限，由它拉起
就是普通权限 —— 安装程序里最常见的换 token 办法，不必自己去复制外壳令牌），
起来之后用 `process_running` 确认；没起来再退回直接启动。

## Task 45: 触摸屏拖不动悬浮球 —— 已交付

### 一、现象与根因

放映时收起的那条胶囊（「悬浮球」）按住就能拖（见 `bindPresentBarDrag`）——
鼠标可以，**触摸屏上不行**：手指一按一拖，它只挪十几像素就停住。

- 根因是 `touch-action` 的**生效值**。它本身不是继承属性，但按规范会与
  祖先链上的取值**取交集**；而这条胶囊不在 `#stage` 里（它在 body 下、
  `position: fixed`），于是拿到的是 `body` 的 `manipulation` ——
  那一条允许浏览器接管平移手势。
- 手指拖动时浏览器认定「这人在滚页面」，立刻发 `pointercancel` 掐断指针序列：
  我们的拖动只走到第 2 个 `pointermove`，而且**收不到 `pointerup`**。
  鼠标不存在「被浏览器接管」这回事，所以这个毛病只在触摸屏上出现。
- 实测（CDP 往页面注入真实触摸事件；这台开发机没有触摸屏，但注入走的是
  浏览器同一条输入管线，手势识别与 `pointercancel` 都会真的发生）：
  `down 1, move 2, cancel 1, up 0`，横向只挪了 24px。

### 二、修法

- [x] `#present-bar` 加 `touch-action: none`（与 `#stage`、`#ink-layer` 取值一致：
  放映时手势归脚本）。光在元素自己身上写不够 —— 关键是这条属性与 `body`
  那条取交集之后的结果。

### 三、验证

| 场景 | touch-action（生效） | pointer 事件 | 位移 | 结论 |

## Task 49: 安装程序在 ARM 机型上卡在 2% 十分钟 —— 已修复

### 现象

ARM 机型（Windows on ARM，x64 要走模拟层）上点「安装」，进度条停在 **2%**
不动，大约十分钟后才继续。

### 根因：2% 那一步在「冷启动一个根本没在跑的应用」

`install()` 的第一步就是 `p.step("正在关闭正在运行的 OpenPPTView…", 2.0)`，
对应 `stop_running_app()`。它原来是**无条件**这么做的：

```rust
if !exe.exists() { return; }
Command::new(&exe).arg("--quit").spawn();   // ← 不管有没有在跑都启一次
for _ in 0..20 { sleep(250ms); if !process_running() { return } }
```

两条叠加在一起：

1. **应用没在跑也照样启动它**。那句「请它退出」实际变成「把 14MB 的 Tauri
   应用连 WebView2 一起冷启动一遍」。ARM 上 x64 要过模拟层，这次启动本身
   就极慢；而安装器这时正阻塞在同一处。
2. **等待写成固定 20 轮**，每轮都 `CreateToolhelp32Snapshot` 枚举全进程。
   在模拟机型上单次枚举不便宜，20 次叠起来就是几分钟。

### 修法

- [x] **先查一次**：没有同名进程就直接返回 —— 新装、应用没开、升级完
  已退出，这三种最常见的情况从此 0 开销（这是本修复的主因）。
- [x] 真有进程时才用 `--quit` 请它退，而且**扔到后台线程去发**：
  `CreateProcess` 会等映像加载完才返回，ARM 上同样不便宜，不能让安装器陪着等。
- [x] 等待改成**时间预算**（4 秒），不再用「固定 20 次」；到点就
  `TerminateProcess` 兜底，宁可丢一次自动存盘也不让安装停在 2%。
- [x] `stop_running_app` 拆出 `stop_app_named(dir, name)`，进程名可注入，
  这样回归测试能用独有进程名，不受开发机上真开着应用的影响。
- [x] 新增回归测试 `stopping_a_not_running_app_returns_at_once`：
  目录里放一个存在但从未运行的 exe，要求整步 < 2 秒（实测 0.02s）。

### 验证

- [x] `cargo test -p ppt-installer --no-default-features`：**4 passed**
  （默认 feature 带 `requireAdministrator` 清单，测试二进制起不来，必须加这个参数）

```rust
let Some(report) = take_pending() else {

};
```

于是每次正常启动都是：建窗口 → 诊断页跑起来 → `crash_ready` → 全进程退出。

- [x] `begin()` 没有待分析报告时只**关掉诊断窗口**，不再 `app.exit(0)`；

- [x] 主窗口改成 `visible: false`，在 `setup` 末尾显式 `show`。

## Task 52: 蓝屏后重启没有触发自检 —— 已修复（0.3.1）

### 现象

蓝屏、重启、进系统，什么都没发生：没有「正在分析」，也没有修复。

### 根因一：换成 Tauri 的 NSIS 打包之后，开机启动就没人登记了

0.3.0 的第一个包是自制安装器打的，它会在安装时登记

- HKLM/HKCU\...\Run → 没有这个值

于是每次登录都只是「什么都没发生」。

### 根因二（这台机器上）：Windows 根本没留下蓝屏记录

同一台机器上核对：

- C:\Windows\Minidump → **空**

也就是说：至少在这一台上，没有可分析的现场。detect() 的判据一直是对的

- [x] **登记搬进应用自己**（crash::ensure_startup，正常启动时执行一次）：

### Task 62：同一场蓝屏被分析两次（0.3.13）

**现象**：一次蓝屏，应用跑了两遍分析；服务器上出现两条「时间差几秒、错误码一样」的记录。

**两个独立成因，各修一处：**

1. **两条检查路径同时开工。** 机器上有两个进程会做这件事：登录时的计划任务
   （带诊断窗口）和老师打开应用时的静默补查。`seen` 是**分析完、包落地之后**
   才写的，管不住「正在分析」—— 两边都读到「没报过」，于是各分析一遍。
   修法：动手前先抢 `%LOCALAPPDATA%\OpenPPTView\crash\claims\<hash>.claim`
   （`create_new` 原子创建）。抢到的负责分析，另一条原地退出。
   锁带 1 小时过期时间，进程被杀也不会永远卡住；`end_run` 里显式放锁。
2. **两条证据各自算一场。** 事件 1001 的时刻与 `Minidump\*.dmp` 的写入时刻
   差几秒是常事。报过事件之后，下一轮检查会从「更新的转储」那边把**同一场**
   再报一遍（id 也因此不同）。修法：`seen` 里额外记 `at:<发生时刻>`，
   10 分钟内的候选一律算同一场（`close_to_reported`）；报事件时顺带把旁边的
   转储一起认下来。真的隔几小时又崩一次不受影响（有测试守着）。

**顺手修的两处：**

- **服务端兜底去重**（`findTwin`）：老版本客户端仍可能报两遍，
  收包时按「10 分钟内 + 错误码相同或一边未知」判重，重复的返回
  `{ok:true, duplicated:true, id:<已有那条>}`，不再落第二份。演示报告不参与。
- **中文错误码进请求头**：`未知（未读到蓝屏事件）` 直接被当成 UTF-8 塞进头里，
  Node 按 latin1 解，落盘成了「æªç¥……」的乱码。客户端改成
  `u:` + 百分号编码（`header_safe`），服务端 `decodeHeader` 解回来。
  线上那条 `20261025-231747` 的乱码已按 latin1→UTF-8 还原成正确中文。

## Task 53: 修复环节超过 20 秒时，可以「跳过此环节」—— 已交付（0.3.2）

### 需求

修复阶段某一个环节跑得久（>20 秒），右下角小条右侧自动出现「跳过此环节」，
点一下结束当前环节、直接进入下一环节。

### 为什么必须留这个出口

`sfc /scannow`、`DISM /RestoreHealth`、`chkdsk /scan` 在慢盘/老机器上都要
十几分钟到半小时。老师是在等着上课，不能盯着一个没有出口的进度条 ——
要么他强杀进程（报告就废了），要么他干脆不用这个功能。

### 做法

- **`SkipControl`**（`crash_repair.rs`）：一个 `AtomicBool` 旗子。命令的
  轮询循环每 400ms 看一次，看到就 `kill` 子进程、把已产出的输出留下、
  记一条「已跳过」，然后跑下一个环节。
- **旗子是一次性的**：`request()` 置位、`take()` 取值即清，并且每进入一个
  新环节还会 `clear()` —— 在 A 环节点的跳过，不能把还没开始的 B 也跳掉。
- **20 秒怎么算**：每个环节挂一条计时线程（`watch_slow`），到点看
  `SlowWatch` 还活着就发事件。用 `Drop` 收旗而不是手工置位，
  命令提前返回（找不到程序、启动失败）也会正常收，不会出现
  「命令早结束了，20 秒后却冒出按钮」的鬼影。
- **界面**：`crash.js` 听 `crash-skip-available` → `body[data-skip="on"]` →
  按钮出现；任何新环节（`crash-phase`）或整轮修复结束（`crash-skip-closed`）
  都立刻收起，点不到过期按钮。点下去先自己禁用，再
  `invoke('crash_skip_step')`，后端返回「有没有环节真的收到」。
- **报告里分得清**：`verdict()` 把「跳过」和「失败」分开写 ——
  跳过是老师主动的选择，不是这一项出问题，混在一起会让看报告的人
  以为系统坏了三处。单条 `Step` 的 `summary` 也写明「跑了 N 秒后跳过」。

### 验证

- [x] `cargo test -p ppt-app`：**27 passed**，新增两条：
  - `skip_stops_the_running_command`：真跑 `ping -n 30`（约 30 秒），
    0.8 秒后请求跳过，断言返回 `< 12s` 且 `skipped=true`（实测整组测试 0.83s 跑完）
  - `skip_flag_does_not_leak_into_the_next_step`：取一次即清 + 新环节 clear
- [x] 界面（CDP 广播与后端同一条事件通道）：`crash-skip-available` 之后
  `data-skip=on`、按钮 `display:block`、尺寸 75×25 @ (261,46)，
  截图确认在右侧且不裁切；再发一个 `crash-phase` 后按钮自动收起
- [ ] 真机上等 `sfc` 满 20 秒点一次（需要管理员权限 + 慢机器，本机没跑真 sfc）

### 追加修复（0.3.10）：点「跳过此环节」没反应

- [x] **根因**：`run_tool` 杀进程后 `join()` 两条读管道的线程。DISM 会自己起

## Task 54: 报告从来没上传过服务器 —— 已修复（0.3.3）

### 现象

蓝屏分析、修复都跑完了，但服务器上一条记录也没有。日志里是
「报告已保存在本地：…\outbox\demo-….zip」。

### 根因：默认地址是空的

`Settings::default()` 里 `endpoint: ""`，而设置页的输入框默认也是空的。
`run()` 的判断是：

```rust
let endpoint = load_settings().endpoint.trim();
if endpoint.is_empty() {
    emit(&app, "local", "没有配置上报服务器，报告已保存在本机");
}
```

于是**只要老师没手动填地址，报告就永远不会发出去**。实测这台机器上
`settings.json` 根本不存在 → 走 `Default` → 空地址 → 每次都只留本地。

设计上把「填地址」当成用户的事，实际结果是零台机器在发 —— 这个功能等于没做。

### 修法

- [x] **内置默认地址** `DEFAULT_ENDPOINT = https://xxccdl.cn/crash/api/v1/crash`
  （就是 Task 50 部署的那台）。`Settings::default()`、`resolve_endpoint("")`
  都指向它；设置页里留空 = 用内置地址，填了就传给学校自己的服务器。
- [x] `load_settings` 对老文件里的 `endpoint: ""` 也做同样的补全 ——
  升级上来的机器不用手动改设置。
- [x] 每个字段单独 `#[serde(default = …)]`：老版本 `settings.json` 少字段时
  不会整份解析失败退回 `Default`，老师**明确关掉**的开关不会被悄悄顶开。
- [x] **采集失败也上报**：`collect()` 出错（没权限读转储、磁盘满）不再
  「分析没能完成」就退出，而是落一份最小报告（`summary.json` + `system.txt`，
  里面写着失败原因），修复照跑、上传照发 —— 「蓝屏了但采不到现场」本身
  就是要告诉服务器的事。
- [x] **打包失败也上报**：`finish()` 失败时用最小报告重打一次再发。
- [x] **应用启动时补发**：`spawn_outbox_flush()` 在 `setup` 里检查 outbox，
  确有 `.zip` 才起线程补送（不为此联网）。以前只有「登录自检且当天没新蓝屏」
  那一条路会补发，老师一直不重启就永远卡着。
- [x] 设置页文案改成「留空就用内置服务器 …… 传不出去会留在本机，下次开机
  或下次打开本应用时自动补发」。

## Task 55: 蓝屏过一次之后就不再自动检查/修复 —— 已修复（0.3.4）

### 现象

第一场蓝屏处理过之后，后面再蓝屏、重启进系统，**什么都不发生**。

现场数据能对上：服务器上那份报告里一次带了**两个** minidump
（`102426-8203-01.dmp`、`102526-6437-01.dmp`）——说明第一次蓝屏那次检查
根本没被触发，第二次才把两场的现场一起收走。

### 根因：用「游标」表示「看到这里为止」

`state.json` 里只有一个 `lastCheck`，检测时按 `epoch >= lastCheck` 过滤：

1. 开机时事件日志（WER 1001）可能还没落盘，`Minidump` 目录也可能还没可读；
2. 这一轮「什么都没看到」，却照样把 `lastCheck` 推到了此刻；
3. 之后每次检查都从那之后开始看 —— **这场蓝屏就被永久跳过了**。

再加上检查只挂在「登录计划任务」这一条路上：任务被组策略禁用、快速启动、
清理软件删任务，任何一种都会让老师看到「蓝屏了，重启后毫无反应」。

### 改法

- [x] 用**指纹去重**取代游标：`state.json` 增加 `seen: []`，记
  `bsod:<发生时刻>:<错误码>` / `dump:<文件名>`。每次固定回看 7 天
  （`LOOKBACK`），靠 `seen` 保证「一次蓝屏只处理一次」——
  查早了没关系，下一轮还会看到。老 `state.json` 只有 `lastCheck`，
  `#[serde(default)]` 照样能读。
- [x] 指纹只在**包已经落地之后**才写入（`mark_seen`），分析中途断电会重来，
  不会丢。
- [x] 报告 id 改用**蓝屏发生时刻**（`stamp(hit.epoch)`），不是「现在」：
  同一次蓝屏无论检查几遍都落在同一个 id 上，服务器不会出现两条一样的记录。
- [x] `detect()` 的挑选逻辑抽成纯函数 `pick_bsod(events, dumps, seen, since)`，
  可以直接测。
- [x] **应用正常启动也补查一次**（`spawn_startup_check`）：查到就静默
  采集 + 上报，不弹窗、不退出应用。不在这条路上跑 `sfc`——
  老师可能正在上课，修复留给下次开机（有窗口那条路）。
- [x] `run(app, report, ui)` 增加 `ui` 参数：没窗口时不发进度事件、
  不缩角、不等动画、**不退出应用**，结束后把 `STARTED` 放下来。

### 新增记录：主板与 HWID

- [x] `system_info()` 增加：`主板序列号`、`系统序列号`、`硬件 UUID`、
  `计算机名`、`机器码`。
- [x] 序列号先读注册表（`HKLM\HARDWARE\DESCRIPTION\System\BIOS`），
  读不到再问一次 SMBIOS（`Get-CimInstance Win32_BaseBoard / Win32_BIOS /
  Win32_ComputerSystemProduct`，约 1 秒，只在采集时发生）。这台 HP 的注册表
  里就没有两个序列号，只读注册表会少掉最有用的两条。
- [x] `To be filled by O.E.M.` / `Default string` / 全 0 全 F 这类占位值
  按「没有」处理，不写进报告。
- [x] `机器码` = SHA-256(`MachineGuid` + 硬件 UUID + 主板序列号 +
  系统序列号 + 计算机名) 前 8 字节，按 `XXXX-XXXX-XXXX-XXXX` 分组。
  重装系统/换硬件会变，但足够回答「是不是同一台机器在反复崩」；
  输入全缺失时写「未知（读不到硬件标识）」，不编假码。
- [x] 两台机器都缺硬件信息时不会撞成同一个码（直接说读不到）。

### 验证

- [x] `cargo test -p ppt-app`：**38 passed**，新增 7 条：
  - `later_bsods_are_still_picked_after_the_first_is_reported`
  - `a_check_that_ran_too_early_does_not_hide_the_event`
  - `dump_is_used_when_the_event_log_is_empty`
  - `ancient_events_are_ignored`
  - `only_the_latest_crash_is_reported` / `older_dumps_do_not_trickle_out_on_every_launch`
  - `old_state_file_without_seen_still_parses`
  - `smbios_placeholders_are_treated_as_empty` / `machine_id_is_stable_and_readable`
- [x] 真机跑 `--crash-report-demo`：服务端 `system` 里能看到

### 追加修复（0.3.9）：第二次蓝屏重启后没有弹窗

- [x] **根因一**：`pick_bsod()` 只要「最近一条 1001 事件已经报过」就整体返回
      `None`，不再看转储。第二次蓝屏如果 WER 事件没落盘（写日志失败、直接断电、

- [x] `detect()` 把「事件 N 条、转储 N 份、已报 N 条」写进应用日志，
      真机再出问题能一眼看出是哪一路没读到。
- [x] 测试：`a_later_crash_that_only_left_a_dump_is_still_reported`、
      `the_dump_of_an_already_reported_crash_is_not_reported_again`。

## Task 57: openFixOS —— 引导损坏时的离线修复（实验性，0.3.5）

### 目标

引导扇区/系统文件被破坏、Windows 已经起不来时，「在 Windows 里跑 sfc」
这件事本身就不成立。这一版给出一条**能回退的**离线修复路径：

1. **开关一打开就装好**（常驻待命）——这一步必须在机器还好的时候做：
   病毒把引导弄坏、系统根本起不来时，已经没有任何机会再「准备」；
2. 原镜像先原样复制一份留作「干净的底」，再复制一份用来改（塞自动修复脚本）；
3. 按 `reagentc /disable` → `/setreimage` → `/enable` 把改造版装进恢复分区；
4. 检测到**引导类蓝屏**（0x7B / 0xED / 0x24 / 0xEF / 0x109 / 0xC0000218 …）时，
   只补一个 `/boottore`（毫秒级）指定**下次启动**进它；
5. openFixOS 里先给 20 秒倒计时（可按 N 跳过），然后自动跑：
   `chkdsk /f` → `sfc /offbootdir` → `DISM /RestoreHealth`
   → `bootrec /fixmbr /fixboot /rebuildbcd`，结果写回 `C:\OpenPPTView\fixos\`；
6. 脚本最后一定 `wpeutil reboot` 回到 Windows；
7. 只有「关闭开关 / 点撤销」才把恢复环境换回原镜像；正常启动**不再**自动卸甲；
8. 修复结果留在本地，随下一份蓝屏报告一起上报。

### 边界（刻意做窄）

- [x] 开关 `bootFix` **默认关闭**（实验性），只在设置页手动打开；
- [x] 只在管理员权限下装机；普通账号运行只分析、不碰引导；
- [x] **不碰 MBR/VBR**：只改 Windows 自己的恢复环境配置（`reagentc`），
      原镜像另有完整备份，`/disable` 暂存的那份也是官方留的退路；
- [x] 任何一步失败都会（`/disable` → 指回干净的底 → `/enable`）还原，
      不留「半截状态」；撤销失败会保留镜像与标记，不会硬删；
- [x] 常驻会接管恢复环境入口：脚本进场先 20 秒倒计时，按 N 跳过直接回 Windows；
- [x] 不自研引导程序/内核：那不是功能，是一个操作系统项目，且写错就是真变砖；
- [x] 恢复环境里不尝试连 WiFi（要机型相关驱动），结果只落本地、下次补发；
- [ ] **遗留**：卸载应用时还没有把恢复环境换回原镜像（需在 NSIS 卸载钩子里调
      `reagentc /setreimage` + `/enable`），现在只能靠用户手动「撤销」。
